OLS v1.0 uses stable identifiers so content can be reused across apps, service books, teaching tools, and archives.

## ID Format

```json
{
  "id": "eotc.kidase.common.block.kyrie"
}
```

## Reference Forms

| Form           | Example                                         | Use                                |
| -------------- | ----------------------------------------------- | ---------------------------------- |
| Local ID       | `block-kyrie`                                   | Same file or same package context. |
| Qualified ID   | `org.openliturgy.eotc.core:block-kyrie`         | Stable cross-package reference.    |
| URN            | `urn:ols:org.openliturgy.eotc.core:block-kyrie` | Long-lived archival reference.     |
| JSON Reference | `{ "$ref": "blocks/kyrie.ols.json" }`           | File-level composition.            |

## ID Rules

| Rule              | Requirement                                                                                    |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| Uniqueness        | IDs MUST be unique within a package.                                                           |
| Stability         | IDs SHOULD NOT change when text is translated.                                                 |
| Versioning        | Breaking textual or structural changes SHOULD create a new version field, not a new random ID. |
| Human readability | IDs SHOULD be descriptive and lowercase.                                                       |
| No spaces         | IDs MUST NOT contain spaces.                                                                   |

## Choosing a Reference Form

Use the least ambiguous form that survives the expected lifetime of the content:

- Use a local ID for tightly coupled files distributed in one package.
- Use a qualified ID when another package may import or cache the entity.
- Use a URN for archival catalogs and external systems that must not depend on a file path.
- Use `$ref` when composing JSON documents and the target is identified by a file or package resolver.

```json
{
  "id": "sec-entrance",
  "type": "section",
  "label": { "en": "Entrance" },
  "blocks": ["block-kyrie", "org.openliturgy.eotc.core:block-trisagion"]
}
```

## How References Resolve

Validators resolve every `$ref` with the same rules, in this order:

1. **Exact ID.** A reference that exactly matches an ID in the package resolves to that entity.
2. **URN.** `urn:ols:<ref>` resolves `<ref>` using these same rules. For backward compatibility, a URN that does not resolve that way is also tried with every `:` replaced by `.` (`urn:ols:eotc:kidase:block:kyrie` → `eotc.kidase.block.kyrie`).
3. **File path.** A reference containing `/` or ending in `.json` resolves to a document inside the package root. Paths that escape the root report `OLS_REF_PATH_ESCAPE`.
4. **Package-qualified ID.** `<package>:<id>` splits at the first `:`.
   - If `<package>` is this package's manifest `package`, `<id>` is looked up locally.
   - If `<package>` is a declared dependency, the reference is **never** satisfied by a local entity with the same `<id>`. Validators report `OLS_REF_EXTERNAL` (info) until dependency resolution is available.
   - Otherwise the validator reports `OLS_DEPENDENCY_UNDECLARED` (error).

Anything else reports `OLS_REF_UNRESOLVED`. The fourth rule matters most when packages are shared: a local `block-kyrie` must not silently stand in for `org.openliturgy.eotc.core:block-kyrie`, because the two may hold different text under different authority.

<Callout tone="info" title="Changed in 1.1">
  Before 1.1, the SDK validators discarded the package prefix and accepted any local entity with the same ID. Packages
  that relied on that behavior should declare the dependency or reference their own package explicitly.
</Callout>

## Renames and Versions

Changing a label, translation, or file location does not require a new ID. When an ID itself must change, publishers should retain a redirect or alias in package metadata so old references can be diagnosed or migrated. A breaking structural revision should update the entity or package version while preserving the stable identity whenever it still represents the same liturgical object.
